> **กลุ่มเป้าหมาย**: นักศึกษาที่รับผิดชอบการพัฒนาฝั่ง Backend (FastAPI & Database Connection)  
> **ภาษา**: ภาษาไทย (Thai)  
> **เป้าหมายหลัก**: เพื่อตอบคำถามอาจารย์ได้อย่างมั่นใจ อธิบายการเชื่อมต่อฐานข้อมูล มาตรการความปลอดภัย การออกแบบ API และความสัมพันธ์ของตาราง

## 1. บทบาทหน้าที่และการแนะนำตัว (30 วินาที)

> "สวัสดีครับ/ค่ะอาจารย์ สำหรับโปรเจกต์ FitBooking นี้ ผม/ดิฉัน รับผิดชอบในส่วนของ **Backend Developer** โดยใช้ **FastAPI (Python)** ทำหน้าที่เป็นตัวกลางเชื่อมต่อระหว่างหน้าบ้าน (Frontend) กับฐานข้อมูล MySQL จัดการเรื่อง **RESTful API**, การควบคุม **Transaction (ACID)** เพื่อไม่ให้เกิดการจองซ้ำ และดูแลความปลอดภัยของข้อมูลทั้งหมดครับ/ค่ะ"

## 2. คำถามหลัก 1: คุณใช้ไลบรารีอะไรเชื่อมต่อฐานข้อมูล? ทำงานอย่างไร?

### แนวทางการตอบ:
เราใช้เครื่องมือหลัก **2 ตัว** ทำงานร่วมกันใน Python:

1. **SQLAlchemy 2.0 (AsyncSession)**:
   - ทำหน้าที่เป็น **Async Engine** และ **Session Manager** จัดการคิวการส่งคำสั่ง SQL แบบ Asynchronous
   - *จุดเด่น*: ช่วยให้เขียนคำสั่งแบบ non-blocking I/O รองรับคนเข้าใช้งานพร้อมกันได้หลายคนโดยไม่ค้าง
2. **aiomysql**:
   - เป็นตัว **Async MySQL Database Driver** ทำหน้าที่ส่งคำสั่งและรับข้อมูลกับ MySQL จริงๆ ผ่านสาย LAN/Internet
   - *Connection String*: `mysql+aiomysql://user:password@host:port/fitbooking`

### สิ่งที่ควรพูดเสริม (ได้คะแนนเพิ่ม):
- **การจัดการ Connection Pool**:
  - ในไฟล์ `backend/app/db/session.py` เราตั้งค่า `pool_recycle=1800` (ทุก 30 นาที) เพื่อป้องกันปัญหาฐานข้อมูล Cloud (เช่น Aiven/RDS) ตัดการเชื่อมต่อเมื่อไม่มีการใช้งานนานๆ
- **Dependency Injection**:
  - ในทุกๆ API เราใช้ `db: AsyncSession = Depends(get_app_db)` ซึ่งข้อดีคือ FastAPI จะช่วยเปิด Session ให้อัตโนมัติเมื่อ Request เข้ามา และปิด Session คืน Connection Pool ให้เองเมื่อทำงานเสร็จ ป้องกันปัญหา Connection รั่ว (Connection Leak)

## 3. คำถามหลัก 2: คุณมีมาตรการรักษาความปลอดภัย (Security) อย่างไรบ้าง?

ถ้าอาจารย์ถามเรื่องความปลอดภัย ให้ตอบ **4 หัวข้อหลัก** นี้:

1. **ป้องกัน SQL Injection แบบ 100%**:
   - เราใช้ **Parameterized Queries (Bound Parameters)** ของ SQLAlchemy ในทุกคำสั่ง เช่น:
     ```python
     text("SELECT * FROM member WHERE user_id = :uid"), {"uid": user_id}
     ```
   - *คำอธิบาย*: เราไม่ใช้การนำ String มาบวกกันเด็ดขาด (`"WHERE user_id = " + input`) ข้อมูลที่ส่งเข้ามาจะถูกส่งแยกเป็นพารามิเตอร์เสมอ จึงไม่สามารถถูกโจมตีด้วย SQL Injection ได้
2. **การแฮชรหัสผ่าน (Password Hashing)**:
   - ใช้มาตรฐาน **`scrypt`** ในการเข้ารหัสรหัสผ่านก่อนบันทึกลงตาราง `users`
   - ในฐานข้อมูลจะไม่มีรหัสผ่าน Plain Text แม้แต่ตัวเดียว
3. **การตรวจสอบสิทธิ์และบทบาท (Authentication & Authorization)**:
   - ใช้ **Bearer Token** ใน Header ของทุก Request ที่ต้องล็อกอิน
   - มีระบบตรวจสอบ Role ชัดเจน: นักเรียน (`MEMBER`), โค้ช (`COACH`), ผู้ดูแลระบบ (`ADMIN`) ถ้านักเรียนพยายามเข้า API ของ Admin ระบบจะตัดสิทธิ์และส่งกลับ `403 Forbidden` ทันที
4. **Data Validation ด้วย Pydantic**:
   - ทุก Input ที่ส่งเข้ามาจะถูกตรวจสอบ Type และ Format ก่อนผ่าน Pydantic Model เสมอ ถ้าส่งข้อมูลผิด Type เช่น ส่งตัวหนังสือในช่องราคา API จะปฏิเสธตั้งแต่หน้าประตูทันที (Validation Error 422)

## 4. คำถามหลัก 3: คุณออกแบบ API อย่างไร?

### แนวทางการตอบ:
1. **มาตรฐาน RESTful API**:
   - แบ่งแยกตาม Resource ชัดเจน เช่น:
     - `/api/v1/bookings` (จัดการการจอง)
     - `/api/v1/orders` (จัดการใบสั่งซื้อและการจ่ายเงิน)
     - `/api/v1/members/me` (ข้อมูลสมาชิก)
     - `/api/v1/coaches` (ข้อมูลโค้ชและตารางสอน)
   - ใช้ HTTP Methods ตามมาตรฐาน: `GET` (ดึงข้อมูล), `POST` (สร้างใหม่), `PATCH` (แก้ไขบางส่วน), `DELETE` (ลบ/ยกเลิก)
2. **โครงสร้าง Response แบบมาตรฐานสากล (Unified JSON Envelope)**:
   - ทุก API ตอบกลับด้วยรูปแบบเดียวกันเสมอ:
     ```json
     {
       "success": true,
       "code": 200,
       "message": "Success",
       "data": { ... }
     }
     ```
   - ช่วยให้ฝั่ง Frontend เขียนตัวรับข้อมูลได้ง่ายและเป็นระบบ
3. **การคุม Transaction (ACID)**:
   - ในขั้นตอนการจอง (`POST /bookings`) มีการกระทำหลายตารางพร้อมกัน:
     1. ล็อกสล็อตเวลาในตาราง `coach_schedule`
     2. บันทึกการจองลงตาราง `booking`
     3. สร้างออร์เดอร์ลงตาราง `orders`
   - ทั้ง 3 ขั้นตอนนี้ถูกครอบด้วย `START TRANSACTION` และ `COMMIT` หากขั้นตอนไหนพัง ระบบจะสั่ง `await db.rollback()` ทันที ทำให้ข้อมูลไม่ค้างครึ่งๆ กลางๆ

## 5. คำถามร่วม: คุณเข้าใจความสัมพันธ์ของตารางเหล่านี้อย่างไร? ทำไมต้องมี Foreign Key?

### ความสัมพันธ์หลักที่ Backend ต้องใช้งาน:
1. **`users` $\rightarrow$ `member` / `coach` (1 ต่อ 1)**:
   - เมื่อผู้ใช้สมัครสมาชิก Backend จะบันทึกตาราง `users` ก่อนเพื่อเอา `user_id` จากนั้นนำ `user_id` ไปบันทึกลงตาราง `member` หรือ `coach` ต่อทันที
2. **`booking` $\rightarrow$ `orders` (1 ต่อ 1)**:
   - เมื่อเกิดการจอง 1 ครั้ง จะมีใบสั่งซื้อ (Order) เกิดขึ้นคู่กันเสมอ โดย `orders.booking_id` ชี้ไปยัง `booking_id`
   - มีสถานะการจ่ายเงินแยกอิสระ (`UNPAID` $\rightarrow$ `PAID`)
3. **ทำไมต้องมี Foreign Key?**:
   - เพื่อให้ Database ช่วยตรวจสอบความถูกต้อง เช่น ป้องกันไม่ให้สร้าง Order ที่ชี้ไปยัง `booking_id` ที่ไม่มีจริง
   - ป้องกันการลบข้อมูลสำคัญผิดพลาด (`ON DELETE RESTRICT`) ถ้ามีประวัติการจองอยู่ จะไม่สามารถลบ Member คนนั้นทิ้งได้

## 6. โพยคำตอบด่วนสำหรับการตอบปากเปล่า (Q&A Cheatsheet)

- **Q: ระบบป้องกันการจองเวลาชนกัน (Double-booking) อย่างไร?**
  - **A**: "ใน Backend เราใช้คำสั่ง `SELECT ... FOR UPDATE` เพื่อล็อกสล็อตเวลาของโค้ชในตาราง `coach_schedule` ไว้ก่อน ถ้ามีคนอื่นพยายามจองสล็อตเดียวกันพร้อมกัน ระบบจะบังคับให้รอ หรือถ้าพบว่าสล็อตนั้นมีคนจองไปแล้ว ระบบจะคืนค่า `409 Conflict` ให้หน้าบ้านทันทีครับ"
- **Q: ปุ่มจำลองการจ่ายเงิน (Mock Pay) ทำงานอย่างไรใน Backend?**
  - **A**: "เราทำ API `POST /api/v1/orders/{id}/mock-pay` ขึ้นมา เมื่อกดปุ่มนี้ Backend จะรัน Transaction ปรับสถานะ Order เป็น `PAID`, ปรับ Booking เป็น `CONFIRMED`, นำยอดเงินไปสะสมใน `total_spend` ของสมาชิก และอัปเกรดระดับสมาชิก (Bronze $\rightarrow$ Silver $\rightarrow$ Gold) ให้อัตโนมัติในฐานข้อมูลครับ"
